# Birdora 8 路专项审核计划

创建日期：2026-07-01

目标：围绕 2026-07-03 的 50 人网页使用峰值，使用 8 个专项审核方向检查 Birdora 当前版本是否可演示、可上线，以及还需要修复什么。

## 审核原则

1. 先只读审核，避免多个 agent 同时改同一片代码。
2. 每个方向输出 P0 / P1 / P2 风险。
3. P0 是两天后必须解决，否则不建议使用。
4. P1 是建议峰值前解决，或至少要有规避说明。
5. P2 是后续增强，不阻断 50 人演示。
6. 审核结论必须落到文件、接口、测试或用户流程上，避免空泛判断。

## 8 个审核方向

### 1. 功能闭环

范围：

- 注册、登录、登出
- 图文发布
- 图片上传和展示
- 跨账号浏览
- 评价、评论、提问
- 作者编辑和删除
- 非作者禁止编辑
- 首页和 `community.html` 两个入口

核心问题：

- A 账号发布后，B 账号是否能看到、评价、评论、提问？
- A 账号是否能修改自己的内容？
- B 账号是否被禁止修改 A 的内容？

### 2. 数据库与持久化

范围：

- SQLite 表结构
- 外键与级联删除
- WAL、busy timeout
- 图片文件和数据库记录一致性
- 测试数据清理
- 并发写入风险

核心问题：

- 页面刷新、服务重启后数据是否还在？
- 删除帖子后互动数据和图片是否一起清理？
- 本地文件存储是否适合 50 人峰值？

### 3. 鸟类识别

范围：

- OSEA 模型加载
- 标签文件
- Top 5 候选
- 低置信度处理
- 上传异常处理
- 文案是否夸大能力

核心问题：

- 当前识别是真模型运行，还是演示假数据？
- 能宣传什么，不能宣传什么？
- `10964` 标签和 `11000` 输出差异是否影响上线话术？

### 4. 性能与 50 人峰值

范围：

- `scripts/test-peak.js`
- 登录、浏览、发布、互动并发
- SQLite 同步 API
- 图片 base64 上传
- ONNX 模型首载
- 静态资源体积

核心问题：

- 当前 50 人测试是否覆盖真实慢路径？
- 图片上传和识别模型首载是否会拖慢峰值？
- 是否需要分离“识别峰值”和“社区峰值”？

### 5. 安全与权限

范围：

- JWT cookie
- CORS
- 限流
- XSS 转义
- 图片 data URL 校验
- 路径穿越
- 私有文件暴露
- 作者权限
- 生产密钥约束

核心问题：

- 非作者是否真的不能改别人内容？
- 上传图片能否绕过类型或路径限制？
- 页面渲染评论/提问是否可能注入脚本？

### 6. 移动端与浏览器体验

范围：

- `index.html`
- `community.html`
- `styles.css`
- `community-post-card.css`
- `script.js`

验收宽度：

```text
360 x 800
375 x 667
390 x 844
414 x 896
430 x 932
768 x 1024
```

核心问题：

- 顶部栏、上传区、发布表单、配图输入、评论/提问面板是否溢出？
- 按钮触控高度是否足够？
- 文本是否互相遮挡？

### 7. 部署与运维

范围：

- Dockerfile
- compose.yaml
- deploy 文档
- Nginx 配置
- PM2 服务
- `.gitignore` / `.dockerignore`
- 生产数据目录
- 图片上传目录
- 备份和回滚

核心问题：

- 生产部署是否会覆盖其他项目？
- 上传图片和 SQLite 是否会被备份？
- 回滚时数据库和文件如何保持一致？

### 8. 测试与文档一致性

范围：

- `AGENTS.md`
- `docs/peak-readiness-handoff-20260701.md`
- `docs/peak-readiness-report-20260701.md`
- README
- CHANGELOG
- package scripts
- `test-auth` / `test-community` / `test-peak` / `test-atlas`

核心问题：

- 文档是否准确反映当前代码？
- 测试是否覆盖用户需求？
- “文案分析”是否被明确标注为未接独立 AI 分析模型？
